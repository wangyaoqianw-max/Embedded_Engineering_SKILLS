# 既有嵌入式工程模块开发工作流（V1.2）

- 版本：V1.2
- 日期：2026-10-21
- 适用：在既有固件中新增模块/功能、修改接口、集成或移植组件、修复缺陷
- 目标：理解已有系统、精准修改、控制影响范围、保留兼容性并提供回归证据
- 定位：面向真实工作中“接到一个模块任务”的执行指南；可同时继承企业级项目的质量、审批与保密要求


## V1.2 延续：模块任务同样使用小循环

任务大小决定切片数量，而不是“模块”二字。**简单低风险修改只需一个设计→实现→验证→反馈循环；跨多个接口或状态路径的模块任务可拆成多项能独立验收的切片，各自执行完整小循环**。不机械地先开发所有驱动层再开发所有业务层。必须尽早对现有调用接口获得运行证据。

先确定真实基线与受影响旧功能；每片通过只代表局部完成，模块任务结束仍要回归现有功能。根因未知的缺陷，必须先复现并建立定向观测，再进入修复切片。若涉及公共 API、持久化格式或全局资源所有权，升级设计/审批深度。

下文每阶段标注现有 Skill 和**尚未开发的研发候选**。企业固件里的模块变更还需继承团队审核、质量和保密要求。


## V1.2 新增：增量文档与交付边界

参见 [工程文档体系与交付约定](documentation-guidelines-v1.2.md)。本流程只对**受影响的权威技术契约**做增量更新，不为一次模块变更复制整个企业文档集；阶段计划、handoff、review 等仍为过程文档，当前有效 API/协议/存储格式应有单一权威来源。

- **检查点 A（M4-F/M6）**：模块或切片完成时检查 API、协议、持久化格式、状态机、资源所有权、错误/超时与兼容规则；有变化则同步规范、调用方及测试，没有则在变更/Review 中记录 `DOC-NONE` 原因。
- **检查点 B（M5/M6）**：跨模块联调时完善必要的集成/配置/测试指引；涉及正式交付时才按接收方需求复核烧录、升级、维护和发布资料，并绑定版本、证据和已知限制。
- 设计批准、代码完成、Host/板级/集成验证分别标注，不以代码存在或阶段 `CLOSED` 推断全部硬件验证通过。

## 1. 核心原则

1. **以现有项目为准**：先读已有规范、设计、源码、工程配置与调用链；不能以通用最佳实践替代已确认的工程事实。
2. **先定变更边界**：只改动需求必要的模块和接口；公共 API、持久化格式、调度模型、全局配置的变化必须明确评估和批准。
3. **以最小可验证变更推进**：一个变更尽量有独立验收与回退方法；拒绝顺带大规模重构。
4. **回归是交付的一部分**：新增功能运行正常，不表示没有破坏现有行为。
5. **缺陷先复现再修复**：若根因未知，先建立证据与可证伪假设；禁止靠猜测直接重写。
6. **证据分级**：区分源码能证明、构建能证明、测试能证明和目标板才能证明的结论。

## 2. 任务入口与执行深度

| 任务类别 | 优先入口 | 特别关注 |
| --- | --- | --- |
| 增加功能或驱动 | 需求 → 阅读 → 接口设计 → 实现 | 与现有模块协作、资源所有权 |
| 局部修改或优化 | 变更影响分析 → 小范围修改 | 兼容性、时序与资源回归 |
| 移植第三方组件 | 版本/许可/依赖调查 → 适配 | 原有接口、工程文件、资源与构建 |
| 根因未知的 Bug | 复现 → 定位 → 修复 → 回归 | 可重复证据与避免引入新缺陷 |
| 简单、低风险的一行修复 | 快速路径 | 仍需必要构建和关联回归 |

如果任务实际上改变了全系统需求、持久化协议、跨模块架构或公共接口，升级为 [企业级固件工作流](enterprise-firmware-v1.2.md) 的相应评审/验证深度，而不是坚持局部路径。

## 3. 标准工作流程

### M0｜接单与变更边界

**本阶段 Skill**：现有可用：[embedded-design-decision](../../skills/embedded-design-decision/SKILL.md)（仅重大设计问题）。**可能开发（未开发）**：embedded-requirements-clarification（变更边界）。


- **输入**：Issue、缺陷报告、需求描述、代码分支。
- **操作**：用必要的反向提问明确期望行为、非目标、目标板与固件版本、外部接口、资源与时序限制、交付方式。识别需求是新增、修改、移植还是排错。
- **输出**：一段可验收的任务定义、受影响功能初判、未知项。
- **出口**：能解释成功条件和“本次不改什么”；关键条件不明则先核实。

### M1｜建立基线与定向阅读

**本阶段 Skill**：现有可用：[embedded-code-reader](../../skills/embedded-code-reader/SKILL.md)，资料不足用 [embedded-resource-acquisition](../../skills/embedded-resource-acquisition/SKILL.md)。**可能开发（未开发）**：暂无：现有读码覆盖。


- **输入**：明确任务、现有仓库和项目规则。
- **操作**：查看 AGENTS.md、README、架构约定、构建 Target 与当前 Git 差异；确认目标版本可以构建/运行或记录已存在的故障。围绕目标接口追踪调用链、配置、数据流、状态转换、ISR/callback、任务和外设所有权。
- **输出**：目标文件/符号清单、当前行为证据、依赖关系及基线状态。
- **出口**：知道在哪修改、谁调用、会影响谁；不会在未归因的原有变更上覆盖他人工作。

理解源码可用 [embedded-code-reader](../../skills/embedded-code-reader/SKILL.md)。有现成代码索引时按项目工具使用；不能把静态引用直接当成运行时行为。

### M2｜影响分析、关键事实与局部设计

**本阶段 Skill**：现有可用：[embedded-design-decision](../../skills/embedded-design-decision/SKILL.md)（设计决策）、[extracting-chip-hardware-facts](../../skills/extracting-chip-hardware-facts/SKILL.md)（板级事实）。**可能开发（未开发）**：暂无：不重复增加局部设计 Skill。


- **输入**：既有接口/数据流、变更要求。
- **操作**：
  - 列出外部调用者、公共头文件、配置/宏、编译条件、启动和初始化顺序、共享状态、ISR/Task/DMA 路径。
  - 明确“谁拥有资源”“何时可访问”“失败如何报告”；检查异常、超时、容量和重试语义。
  - 涉及外设时核对板卡引脚、时钟、DMA 映射、IRQ、电气及适用 Errata；硬件事实与软件推断分开。
  - 确定最小改动与验收策略；确需改变 API、存储布局、接口兼容或架构时发起所需的设计评审。
- **输出**：局部设计或简短变更说明、影响面、风险与验证清单。
- **出口**：关键边界清楚；没有未经批准的外部行为改变。

需要选择方案时调用 [embedded-design-decision](../../skills/embedded-design-decision/SKILL.md)；资料缺项和硬件确认按需使用 [embedded-resource-acquisition](../../skills/embedded-resource-acquisition/SKILL.md)、[extracting-chip-hardware-facts](../../skills/extracting-chip-hardware-facts/SKILL.md)。

**M2 文档影响分析**：查找现存的接口、协议、内存/存储规范和调用方契约。需要改变公共格式或可观察行为时，列出应更新的权威文件与兼容性风险，按项目审批后实施；不得只改 Stage `design.md` 而让长期规范过期。

### M3｜切片计划和失败基线

**本阶段 Skill**：现有可用：[embedded-design-decision](../../skills/embedded-design-decision/SKILL.md)（实施路线）、[embedded-code-reader](../../skills/embedded-code-reader/SKILL.md)（确认影响）。**可能开发（未开发）**：embedded-task-decomposition、embedded-debugging（失败前态）。


- **输入**：改动边界与验证条件。
- **操作**：把较大功能拆为有限的纵向切片；每个切片声明依赖、可观察行为和验收方法。Bug 修复应优先获得最小可复现用例或可重复测量的故障信号；无法稳定复现时记录频率、触发条件与证据限制。
- **输出**：小范围修改计划、回归对象、可复现或可测量的前态证据。
- **出口**：下一步可单独验证，知道怎样证明“比原来更正确”。

### M4｜每个切片的设计—实现—验证—反馈小循环

**适用范围**：既有工程模块的每个可验证子任务；如果无法合理拆分，则将整个任务视为一个切片。已有通过验证的切片是下一切片的基线。**小循环必须发生在每个切片内部，而不是做完全部设计和编码后只验证一次。**

#### M4-D｜Design：切片局部设计

- **输入**：该切片目标、外层确认的接口与硬件事实、已通过的前置切片。
- **动作**：确认需要修改的范围、接口/任务/ISR/DMA 与资源所有权、核心状态流、正常与关键失败路径；为本片制定测试输入、预期结果、环境与失败判据。
- **输出及出口条件**：简短切片设计卡（目标/非目标、边界、取舍、验收用例、前置依赖）；没有会改变实现的关键未知项。
- **已有 Skill**：[embedded-design-decision](../../skills/embedded-design-decision/SKILL.md)（有实质设计取舍时）；[embedded-code-reader](../../skills/embedded-code-reader/SKILL.md)（已有工程需核对调用关系时）。
- **未来候选 Skill（未开发）**：embedded-requirements-clarification（仅歧义阻碍设计时）；不再另造重复的设计 Skill。

#### M4-I｜Implement：最小编码与构建

- **动作**：只实现当前切片的可观察行为；同步必要工程文件/配置，遵守项目架构和生成代码边界。纯逻辑或可控测试接缝适合 Red → Green → Refactor；不要求所有硬件依赖路径都先写 Host TDD。
- **输出及出口条件**：本片 diff、实际 Target 的构建结果和可供测试的产物；**编译通过不是验证通过**。
- **已有 Skill**：[embedded-code-development](../../skills/embedded-code-development/SKILL.md)。
- **未来候选 Skill（未开发）**：暂无新编码 Skill 需求；避免复制现有 Implement/Modify/Port。

#### M4-V｜Verify：实际执行验收

- **动作**：运行计划中的 Host 测试、目标板功能/边界/异常用例和必要时序/资源测量。对 DMA、ISR、RTOS、OTA/Flash 等行为，应依据风险取得 J-Link/RTT/逻辑分析仪/复位与故障注入等真实证据。
- **输出及出口条件**：记录环境、版本、输入、预期、实际、证据位置和 PASS/FAIL/BLOCKED。源码证据、编译、Host、板级、系统回归分别报告；没有执行不得写 PASS。
- **已有 Skill**：[embedded-code-development](../../skills/embedded-code-development/SKILL.md) 负责已批准的局部测试入口、模块自测和实现相关检查；**尚无独立测试执行 Skill**，仍需真实工程工具和人员执行。
- **未来候选 Skill（未开发）**：embedded-test-verification（独立执行、记录并核对测试证据）。

#### M4-F｜Feedback：分析结果、修正、回归、关闭切片

- **PASS**：对照需求/工程规范做轻量自检并保存已验证 commit、测试证据与任务状态，然后开始下一项依赖切片。
- **FAIL**：保留最小复现和观测；实现缺陷回 M4-I；局部接口/算法错误回 M4-D；若波及公共 API、存储格式或全局资源所有权，则升级到外层设计/批准阶段，同时检查之前通过的切片是否受影响。
- **BLOCKED**：说明缺失设备、环境或依赖及恢复条件；不允许假设测试通过或推进依赖任务。
- **已有 Skill**：[embedded-code-reader](../../skills/embedded-code-reader/SKILL.md)（读码定位）、[embedded-design-decision](../../skills/embedded-design-decision/SKILL.md)（需要回设计时）、[embedded-code-development](../../skills/embedded-code-development/SKILL.md)（明确缺陷后修复）。
- **未来候选 Skill（未开发）**：embedded-code-review（独立审查）、embedded-debugging（根因不明）、embedded-work-handoff（长任务交接）。

**退出条件**：本切片验收证据成立，且与已验证基线的必要兼容检查通过。**所有切片通过仍需外层跨切片集成回归与交付/复盘。**

**模块完成文档检查点 A**：对照本次 diff、已批准设计和实际测试报告，确认应更新的接口/协议/格式规范及调用方示例；不能仅凭生成文档宣布接口已验证。无影响则在现有阶段结果中记录 `DOC-NONE`，避免无意义新文件。

### M5｜跨切片集成与目标板回归

**本阶段 Skill**：现有可用：[embedded-code-reader](../../skills/embedded-code-reader/SKILL.md)（故障定位辅助）、[embedded-code-development](../../skills/embedded-code-development/SKILL.md)（必要修复）。**可能开发（未开发）**：embedded-test-verification（回归证据）。


- **输入**：变更 diff、原始失败/成功条件、影响范围。
- **操作**：
  - 验证新增/修复的正常、边界及关键异常行为。
  - 测试直接调用者、共享资源、受影响任务/中断、配置变体和旧接口行为。
  - 涉及 UART/DMA/RTOS/存储/升级时按风险检查回绕、并发、延迟、溢出、复位、掉电与恢复。
  - 对照修改前基线解释差异；日志/断点只证明观测到的事实，不代替所有板级或电气验证。
- **输出**：回归结果、构建 Target、硬件环境、测试条件与证据、残余风险。
- **出口**：本次变更与受影响旧功能完成约定验证；未测项明确标注。

**集成/交付文档检查点 B**：核对受影响的构建配置、下游集成步骤和跨版本兼容；如果本任务包含正式对接或交付，再同步接收方所需的 API/协议、烧录/升级说明与变更记录。不涉及正式交付时，保持模块增量说明即可。

### M6｜双维审查、交付和简短复盘

**本阶段 Skill**：现有可用：[embedded-code-reader](../../skills/embedded-code-reader/SKILL.md)（只读理解，不等于审查）。**可能开发（未开发）**：embedded-code-review、embedded-work-handoff。


- **输入**：代码差异、需求/设计约束与测试结果。
- **操作**：
  1. **Spec 审查**：实现是否满足任务原意，包括错误语义与边界条件？
  2. **Standards 审查**：是否符合既有架构、资源所有权、编码规范、实时性与安全约束？
  3. **Evidence 审查**：声称通过的构建、功能与板级验证是否确有可核对的证据？
  4. 清理临时调试代码和无关变更，按项目流程提交 PR/变更说明并完成授权审查。
- **输出**：变更摘要、影响文件/接口、测试与审查结论、未解决风险。
- **出口**：达到团队或项目约定的合入/交付条件，可回退、可追踪。

## 4. 专用分支：根因未知的运行故障

**该分支 Skill**：现有：[embedded-code-reader](../../skills/embedded-code-reader/SKILL.md)（分析源码与调用）、[embedded-code-development](../../skills/embedded-code-development/SKILL.md)（根因明确后实施修复）；**可能开发（未开发）**：embedded-debugging（复现→假设→观测→修复→回归）。

不要直接按“理解代码 → 猜测修改”处理。采用下列闭环：

1. **复现**：固定固件版本、设备、输入、时序和故障现象；可重复时保留失败测试或测量脚本。
2. **缩小**：确认故障边界（启动、ISR、RTOS、驱动、协议、存储）；查最近相关变更，排除无关变量。
3. **假设**：列出最多几项可证伪原因，以及每项成立时应出现的观测结果。
4. **定向观测**：使用 J-Link 断点、PC/LR/SP/CFSR、RTT/日志、计数器或逻辑分析仪定位；中断与时序敏感故障需注意调试行为本身改变现场。
5. **最小修复**：在最可能根因已被证据支持后修改，并验证原故障消失。
6. **防复发**：保留可行的回归测试，检查相邻路径，移除临时注入/日志，记录根因与证据。

若故障无法稳定复现，不得直接声称“已彻底修复”；应说明验证覆盖和仍存在的不确定性。

## 5. 实际工作中的轻量快速路径

仅限边界明确、低风险、小范围的任务：

**核对需求 → 查看相关源码与当前 diff → 说明影响范围 → 最小修改 → 构建与关联测试 → diff 自检与提交。**

以下情形不得自动套用快速路径：公共 API/协议变更、数据持久化、固件升级、共享状态/ISR/DMA 并发、安全保护、未知硬件事实或故障根因未定位。触发这些条件时回到 M1–M6 的适当深度。

## 6. AI 协作与交付约束

更换模型或 Agent 时，按[模型无关的 AI 工程执行与交接约定](model-agnostic-ai-execution-v1.2.md)核实当前 Commit、未提交变更、允许修改的接口与文件、既有失败基线及未执行验证；交接信息与仓库不一致时先停止相关修改并查证。

- AI 在阅读与设计阶段提供可定位源码证据（路径、符号、行号），并区分事实/推测/未知；不能虚构代码路径和硬件测试。
- 进入编码前确认范围；AI 不应未经批准顺带重构、增加新工具或修改仓库级配置。
- 独立审查需求符合性与规范符合性，并要求报告未测试内容；同一 AI 的判断不能替代真实测试。
- 变更接口、删除文件、烧录/发布、外部写入或上传企业资料，须遵循现有授权与保密规则。
- 跨会话交接保留：任务目标、基线 commit、已修改文件、当前编译/测试结果、未解问题和下一步验证；不依赖聊天历史接续工作。

## 7. 模块任务 DoD

- [ ] 需求与影响范围明确，未做无关重构。
- [ ] 新旧接口、资源所有权、时序和错误语义符合项目约束。
- [ ] 必需的代码/工程文件/配置同步完成。
- [ ] 构建及局部测试有记录，硬件相关行为有真实板级证据或标明未验证。
- [ ] 受影响旧功能已回归；已知风险明确。
- [ ] 文档影响已检查：受影响的权威 API/协议/存储规范同步更新，或记录 `DOC-NONE` 原因；必要的接收方交付材料和版本/验证限制已核对。
- [ ] 代码差异可读、审查完成、提交与回退路径清楚。

## V1.2 Skill 开发方向与约束

跨三套流程最值得先试验的候选是 **embedded-task-decomposition**（把设计拆成可验证切片）、**embedded-test-verification**（独立执行并核实 Host/板级/回归证据）、**embedded-code-review**（分开 Spec/Standards/Evidence 审查）。**embedded-debugging**（根因未知）、**embedded-requirements-clarification**（需求歧义）、**embedded-work-handoff**（跨会话长任务）按实际高频失败场景再决定是否开发。

**这些都尚未开发**；不要调用不存在的 Skill。一个候选 Skill 只解决一个独立、重复的工程问题；先建立失败基线，再按仓库 [AGENTS.md](../../AGENTS.md) 验证显式触发、隐式触发、误触发与核心行为。完整路线图在 [工作流索引](../README.md)，参考 [Matt Pocock 的方法](https://github.com/mattpocock/skills) 和 [本仓库设计框架](../../skills/embedded-design-decision/references/decision-framework.md)。
