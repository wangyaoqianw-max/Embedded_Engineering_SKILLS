# 模型无关的 AI 工程执行与交接约定（V1.2）

- 版本：V1.2
- 日期：2026-10-30
- 适用：本仓库 V1.2 的个人项目、企业固件、既有工程模块三条工作流
- 定位：跨模型、跨 Agent、跨会话的工程执行与交接规则；是工作流指导文件，不是自动执行的 Skill

## 1. 目标与边界

将工程目标、技术契约、任务状态及验证证据从特定 AI 模型、Agent 产品和聊天历史中剥离，使新的执行者可以基于仓库资料继续工作。

**模型可替换不等于模型能力等价；任务可移植不等于结果必然一致。** 本规范追求可理解、可交接、可检验，而非要求不同模型输出相同代码或使用相同工具。

本规范补充而不替代 [个人项目](personal-project-v1.2.md)、[企业固件](enterprise-firmware-v1.2.md)、[既有模块](existing-module-v1.2.md) 的开发循环；文档分类和单一权威来源仍遵循 [工程文档体系与交付约定](documentation-guidelines-v1.2.md)。项目/组织已批准的规范、权限、安全及保密要求优先。

## 2. 工程协议与执行者分离

| 层次 | 责任 | 不应承担的职责 |
| --- | --- | --- |
| 工程协议层 | 需求、已批准设计、公共接口、资源与时序约束、任务契约、验收及交接 | 不绑定某一个模型、专有提示词或调用方式 |
| Agent 适配层 | 将工程任务映射到所用产品的上下文加载、文件访问、终端、构建和调试能力 | 不擅自修改工程契约或宣布未执行测试通过 |
| 执行层 | 在授权范围内分析、设计、编码、测试或审查，提交结果及证据 | 不把自己的推断、内部记忆当作项目事实 |

普通聊天模型可能只能给出代码或计划，工程 Agent 可能具备仓库读写、命令执行能力；必须按当前工具的实际权限组织工作。不能因为某模型理解任务，就假定它有本地 Keil、J-Link 或目标板访问能力。

## 3. 工程上下文外置与权威性

- **稳定事实**：代码、构建配置、板卡资料、权威 API/协议/存储规范及已批准设计应有可定位来源和版本；按项目现有目录维护，不为 AI 另建一份重复规范。
- **过程事实**：任务进度、ADR、变更说明、测试记录、handoff 记录应可回溯到对应代码基线、工具环境与证据。
- **临时上下文**：聊天记录、Agent 记忆、自动摘要和个人提示词可辅助理解，但不能替代经过确认的工程资料。
- **冲突处理**：新执行者如发现交接叙述与仓库现状、批准契约或测试证据冲突，应先核实并记录差异；禁止静默以旧聊天记录或模型猜测覆盖事实。

跨模型接续时优先提供仓库、任务入口及所引用的权威资料，而不是倾倒全部旧对话。资料不足时明确提问或标记 BLOCKED。

## 4. 编码前的最小任务契约

任务可记录于现有 Stage、Issue、PR 或任务卡，不强制新建 Markdown。进入 Implement 前至少明确：

1. **目标与非目标**：要交付的可观察行为，以及本次不解决的事项。
2. **可重现基线**：仓库、分支/Commit、工作区未提交变更、构建 Target 与必要依赖。
3. **设计来源**：适用需求、已批准决定、API/协议/存储规范、芯片及板级事实的引用。
4. **变更边界**：允许修改的文件/模块、禁止更改的公共契约、生成代码及配置限制。
5. **运行约束**：ISR/Task/DMA 资源所有权、并发、时序、内存、超时、错误及恢复语义。
6. **验收契约**：测试输入、预期、失败判据、可用 Host/板级环境、必须保留的回归项。
7. **授权与未知项**：需要人工批准的外部写入、烧录、删除、推送及发布；尚未确认的问题。

契约只引用已有正式技术规范，不复制第二套版本。低风险独立任务允许压缩成几行；OTA、Bootloader、并发、存储一致性等高风险任务应明确关键失败路径，不能用笼统的“实现并测试”代替。

示意性任务卡（内容为模板字段，不表示实际工程已经验证）：

```text
Task ID / 目标与非目标：
Baseline / Target / 已有未提交变更：
权威契约与证据引用：
允许修改 / 禁止修改：
资源所有权 / 异常与时序约束：
测试输入、预期与失败判据：
工具能力、权限与需批准操作：
未决事项与阻塞条件：
```

## 5. 分配任务与执行前检查

- **不按模型品牌固定分工**：需求与架构不确定时优先保证推理、资料核实与审查质量；边界清楚的常规实现可以比较不同模型的正确率、返工与总成本。低调用成本不必然带来低工程成本。
- **能力前检**：执行者应说明实际能够访问的源码、终端、工具链、测试设备和网络资源；无法访问的能力标为不可用，不模拟为已执行。
- **遵守审批边界**：公共 API、存储/升级格式、全局配置、安全策略、共享资源所有权的变更须返回设计/审批流程；不能以“优化实现”为由越界重构。
- **最小变更**：只修改当前切片必要内容；并行 Agent 对公共接口、共享状态和集成基线必须有明确负责人，避免相互覆盖。
- **保密与权限**：模型切换不自动授权将企业源码、证书、密钥、客户数据等传给新的外部服务。

## 6. 验收独立于模型自我评价

验收标准应尽量在编码前确定，并以实际执行结果判断。实施者可以编写和运行测试，但自身宣称“代码正确”不能替代独立证据。

| 验证层级 | 可以说明什么 | 不能据此推定什么 |
| --- | --- | --- |
| 源码/静态检查 | 所审查范围内的结构、约束或静态问题 | 已成功编译或运行 |
| 实际 Target 构建 | 指定配置与工具链构建成功 | Host、板级功能正确 |
| Host 测试 | 给定主机环境及测试用例通过 | 外设、时序或目标板行为正确 |
| 目标板测试 | 指定板卡、固件及条件下用例通过 | 跨模块、长稳、异常恢复全部通过 |
| 系统集成/回归 | 在记录的系统配置下相关测试通过 | 未覆盖环境及全部潜在故障都不存在 |

报告实际版本、环境、输入、预期、结果、证据位置和未测项；采用 PASS / FAIL / BLOCKED / NOT RUN 等明确状态。工具或硬件不可用时应移交验证任务，不得将未执行测试记为 PASS。高风险固件应按风险加入复位、掉电、超时、竞争条件和故障注入验证。

## 7. 跨模型 / Agent 交接

发生会话中断、模型切换、执行机器更换或多人接手时，最小交接记录应包含：

- 任务 ID、目标、当前状态及其前置依赖；
- 基线 Commit、分支、工作区未提交变更与已修改文件；
- 适用的批准决策、接口及行为约束（以权威来源链接为准）；
- 已执行的构建/测试、实际结果、证据与尚未运行的测试；
- 当前失败现象、未解决风险、阻塞原因及下一项可执行操作；
- 该操作的验收条件、需要的工具/权限和回退方式。

接收者先核对实际仓库和证据，再继续任务。交接记录只陈述当前事实，不把预测结果、聊天总结或上一执行者的自我评价冒充已验证状态。记录深度按任务风险裁剪，不要求完整复制每轮对话。

## 8. 跨模型可移植性实验

可从已有可复现基线、接口明确且有独立验收的模块开始实验。不要首先选无法安全复位或缺少板级验证条件的高风险任务。

1. 固定同一份任务契约、起始 Commit、构建/测试环境及验收标准。
2. 让不同模型/Agent 从相互隔离的工作区执行，不提供前一个模型的聊天历史；明确各自真实工具权限。
3. 比较任务理解偏差、关键澄清次数、越界修改、构建与测试结果、人工返工、完成时间和总成本。
4. 对失败归因：工程资料缺失、工具能力/权限不足、模型推理或执行错误、测试环境阻塞；不要混为一个“模型不行”。
5. 将重复出现的缺陷反馈到任务契约、权威规范、验证入口或工具适配；只有有稳定重复需求时再评估开发独立 Skill。

**待验证假设**：清晰的设计与验收契约可能缩小不同模型在常规实现任务中的表现差距。未经过同条件实验前，不将该假设当作已证实结论。

## 9. 与 V1.2 工作流和 Skill 的关系

三套 V1.2 工作流继续决定阶段、切片、设计深度、质量门禁和交付；本规范仅补充跨执行者的输入、能力检查与交接。原有 [工程文档指南](documentation-guidelines-v1.2.md) 继续负责规范生命周期与证据一致性。

现有 `embedded-code-development`、`embedded-code-reader`、`embedded-design-decision` 等 Skill 仍按各自职责使用。本文件本身不是 Skill，也不表示 `embedded-work-handoff` 或其他候选 Skill 已开发。若未来需要适配不同 Agent，可保留项目中的轻量入口说明，但不得分叉维护相互矛盾的工程契约。

**最小验收**：其他执行者不读取原对话，仅凭仓库资料与任务入口，能够说明任务目标、约束、当前基线和下一步验证；无法继续时能够具体指出缺少的事实、权限或环境。
