# 嵌入式工程文档体系与交付约定（V1.2）

- 版本：V1.2
- 日期：2026-10-21
- 适用：本仓库 V1.2 的个人项目、企业固件、既有工程模块三条工作流
- 定位：研发过程文档、长期有效技术规范、交付文档的分类、产出时机和一致性规则；这是工作流指导文件，不是自动执行的 Skill

## 1. 原则与边界

**按模块沉淀、按集成完善、按版本发布。** 文档是工程产物，不是最后统一补写的宣传材料。接口、协议、持久化格式等契约在相关设计获确认时即可建立；随着代码实现和实际验证更新状态；集成指南、烧录/升级手册和发布说明在其依赖的功能与环境具备证据后完善，正式发行前复核。

**按职责分类，不按阅读者是人还是 Agent 分类。** 工程师与 Agent 可共享同一权威文档。文档应服从适用的项目/组织流程、保密要求、法规与安全约束；本指南不替代正式审批或行业认证文档。

文档深度按风险、复杂度、协作边界裁剪：没有独立技术契约变化的简单修复只需必要的变更及验证记录，不强制新建 Markdown。文档变更检查是必选动作，**新增文档并非必选结果**。

## 2. 两类文档与一套共享的正式技术规范

| 类别 | 核心目的 | 典型实例 | 维护方式 |
| --- | --- | --- | --- |
| 研发过程文档（Process Documentation） | 解释目标、决策、施工、交接、审查、实际证据；支持跨会话/跨人员续接 | 需求/阶段设计、实施计划、任务状态、ADR、handoff、review、验证记录 | 跟随阶段与变更形成可追溯历史；不把聊天记录当成冻结事实 |
| 正式工程技术规范（Authoritative Engineering Specifications） | 定义当前有效的长期契约和实现约束 | 架构、模块设计、内部 API、通信协议、存储/镜像格式、RTOS/内存约束 | 一个权威来源；设计确认后建立，随实现与兼容变更更新 |
| 交付文档（Deliverable Documentation） | 让接收方独立集成、使用、部署、验证和维护 | 对接协议、SDK/API 说明、集成指南、烧录/升级操作、故障维护、测试摘要、Release Notes | 绑定适用固件/板卡/协议版本；对外发放前核对完整性与证据 |

逻辑上划分为**过程资料**与**交付资料**两类；中间的正式技术规范是两类用途共享的权威内容，**不是额外复制的一套文档**。例如 API/协议规范既可供内部开发，也可经范围审查交付其他软件团队；完整内部设计和日志不应自动对外发放。

测试方案通常用于过程控制，验证原始记录是过程证据；经审核的测试摘要或测试报告可以成为交付文档。不要把执行日志等同于测试通过。

## 3. 分类时先问四个问题

1. **谁依赖这个信息？** 只为阶段续接、审查，还是有跨模块/跨团队的稳定消费者？
2. **是否形成工程契约？** 接口、数据格式、超时、所有权、异常/兼容语义若被其他模块依赖，应进入权威规范，不只埋在某个 Stage 的 `design.md`。
3. **是否有明确接收方与用途？** 其他软件团队、硬件、测试、生产、售后或外部集成方需要什么资料，不按部门名称机械生成全部清单。
4. **当前能核实到什么程度？** 已批准设计、已实现、Host 已验证、板级已验证、集成已验证必须分别陈述；信息缺失时说明限制，不编造完整手册。

## 4. 文档清单与最小内容

| 文档 | 何时需要 | 至少回答什么 |
| --- | --- | --- |
| 项目 README / 构建入口 | 项目可交接或他人需要复现工程时 | 目标、依赖、实际 Toolchain/Target、构建入口、配置与限制 |
| 需求与验收定义 | 有待实现的功能/约束时 | 期望行为、边界、不做什么、异常条件、可观察验收 |
| 架构/模块设计 | 存在实质设计或系统协作时 | 模块职责、数据/状态流、ISR/Task/DMA/共享资源所有权、取舍 |
| 内部 API 契约 | 有公共 API 或需要稳定调用方时 | 参数/返回值、调用上下文、阻塞/异步完成语义、数据生命周期、线程安全、超时与错误 |
| 通信协议/寄存器映射/GATT 规范 | 自定义报文或与独立端点对接时 | 链路与编码、字段/字节序、命令、状态、超时、重试、错误、版本兼容、合法/非法样例 |
| 存储/镜像/升级格式 | 存在持久化、Bootloader、OTA 或升级兼容需求时 | 分区、Header/Metadata 字段、大小/校验、写入提交、断电恢复、兼容/迁移 |
| 硬件软件接口规范 | 软硬件边界需共同确认时 | 引脚/网络、时钟、IRQ/DMA、电气/复位/启动限制、板卡版本及来源 |
| 测试计划与验证报告 | 需要证明功能/可靠性时 | 环境/版本、输入、预期、实际、PASS/FAIL/BLOCKED、证据与未测项 |
| 集成/配置/烧录/升级/维护指南 | 下游需要实际操作、且依赖路径已确定时 | 前提、工具版本、命令/操作、成功判据、失败处置、恢复与风险 |
| 版本清单与 Release Notes | 候选版本准备交付时 | 目标版本/板卡、变更范围、兼容性、产物来源/哈希、验证边界、已知缺陷及回退 |

文档可合并；接口规则若能由头文件注释直接准确表达，头文件可作为权威契约，独立 Markdown 只做索引或向跨团队接收方提供必要说明。已有标准协议（如 Modbus）不应被重复发明；项目文档应描述实现支持的功能码、寄存器、编码和例外行为。

## 5. 触发时机：两个检查点

### A. 模块/切片完成检查（内层反馈 / 模块审查）

检查本次是否创建或修改了：公开 API、模块职责或架构、执行上下文和资源所有权、协议字段/寄存器/GATT、存储/镜像/Metadata、超时/错误处理、兼容规则，以及调用方依赖的行为。

- **需要更新**：在当前模块或相关设计完成并核对测试证据后，同步对应权威技术规范；标明其实现/验证状态，确保调用者可依据它工作。
- **无需更新**：记录 `DOC-NONE` 及理由（可写入现有 review、handoff、PR/任务记录），不自动生成空白文档。
- **影响公共契约**：先走项目设计审批/影响分析，核查已有消费者和回归范围；不能由实现者或 Agent 在代码里擅自改变冻结约束。
- **验证不足**：允许保留 Draft 或带明确“已实现、待板测”的规范；不得把它称作已验证的交付能力。

### B. 集成/版本交付检查（外层系统验证 / 发布审查）

按实际接收方与交付范围，确认是否需要集成、配置、烧录、升级、维护、测试摘要、版本说明等资料。

- 在关键模块可独立操作时可以先形成局部指南；其状态是草稿/限定范围，不代表完整产品手册。
- 系统集成时校验跨模块接口、工具链、配置、固件镜像与兼容关系；不能凭单模块通过声明整体可用。
- 发布时按目标版本/硬件修订和使用环境核对步骤、输入/输出、失败与恢复路径、验证摘要、已知限制和授权审批。
- 文档可以是经审核的权威规范复用/导出加少量专用指南；避免维护两套容易分叉的相同字段表。

## 6. 建议的状态与可追踪信息

不要用一个 `DONE` 混合三个维度：

| 维度 | 典型值 | 含义 |
| --- | --- | --- |
| 文档审查状态 | Draft / Reviewed / Approved / Obsolete | 是否经过规定的内容审查或批准 |
| 实现状态 | Planned / Implemented / Partially Implemented / Not Implemented | 代码是否落实了约定 |
| 验证状态 | Not Run / Host PASS / Board PASS / Integration PASS / Partial / Fail / Blocked | 已有哪些真实证据；可多层并列，不能互相代替 |

对跨团队/长期文档建议在页首记录：标题、用途与适用范围、负责者/审核者、适用软硬件及协议版本、对应需求/设计/代码 Commit、最新更新日期、状态、证据或验证报告位置及已知限制。简单文件可以省略不必要字段，但不能省略会误导接收方的版本和状态。

追溯链：`Requirement → Design/ADR/Contract → Code/Commit → Test Evidence → Release/Deliverable`。不要虚构缺失的链接、测试编号、哈希、审核签字或版本。

## 7. 路径与存储策略

以**目标项目现有约定优先**，不强制目录重构。参考 [STM32F4_Bootloader_OTA_Test_Project](https://github.com/wangyaoqianw-max/STM32F4_Bootloader_OTA_Test_Project) 的既有分工：

| 项目位置 | 适合存放 |
| --- | --- |
| `00_Project/03_Stages/<stage>/` | `design.md`、`implementation_plan.md`、`handoff.md`、`review.md` 等阶段过程文档 |
| `00_Project/04_Decisions/` | 跨阶段长期有效的 ADR |
| `03_Firmware/00_Doc/` | 架构、模块设计、API、协议适配、存储/Memory 等正式技术规范 |
| `04_Test/Reports/` | 完整测试证据和正式验证记录 |
| `01_Reference/` / `02_Hardware/` | 厂商/外部协议、原理图等输入资料，不冒充自研交付规范 |
| `06_Output/` | 生成固件、升级包、日志和按项目约定形成的发布包；默认被忽略时**不应作为正式技术规范唯一副本** |

对外资料可按项目约定生成交付包、导出 PDF 或维护独立交付区；源规范应受版本控制，交付资料必须指向对应版本。是否把敏感实现、私有 API、完整日志对外共享由项目责任人批准。

## 8. 文档更新与一致性检查

每次代码评审/模块关闭和版本发布检查：

1. **变更影响**：扫描变更是否影响 API、协议、存储格式、初始化/调度、资源所有权、时序、错误与升级兼容。
2. **唯一权威**：确定应修改哪份规范；阶段记录保留“为何变化”，权威规范保留“当前有效内容”。
3. **双向核对**：对照已批准需求/设计核对代码是否符合；对照实际代码与测试证据核对文档宣称；不能从代码反推设计再宣称需求得到验证。
4. **版本与消费者**：说明旧固件、上位机、其他模块、Bootloader/Application、硬件版本是否兼容；必要时同步示例报文、工具、测试与接收方。
5. **结果**：记录更新文件和 Commit，或 `DOC-NONE` 原因；差异、未测项、待批准项不得静默关闭。

特别提醒：文档正确不等于实现正确；编译 PASS 不等于 Host PASS，Host PASS 不等于板级 PASS，板级局部 PASS 不等于系统回归 PASS。

## 9. Bootloader/OTA 示例（解释策略，不作为新实测结论）

- **S07 镜像存储/OTA 服务完成**：可建立镜像 Header、Slot、Metadata、API/错误语义及升级流程的正式规范；记录实现与验证边界。
- **S09 固件安装及 S10 Trial/Confirm/Rollback 发展**：完善启动状态机、原子提交、掉电恢复和跨版本契约；若后续变更前述格式，同步修改单一权威规范和回归测试。
- **集成/发布阶段**：在实际工具链、固件包、镜像与板卡条件可复现时，完成烧录/升级/回退指南和 Release Notes。若未获得连续 Bootloader 运行证据或某项板测未完成，交付说明如实注明，不得转述为“全部硬件验证通过”。
- **A/B 语义**：此示例工程 W25Q64 的 A/B 为外部固件镜像槽，执行中的 Application 位于内部 Flash，不能将外部槽误写为 MCU 可直接执行的双应用分区。

## 10. 最小完成条件（按风险裁剪）

**模块/切片 DoD**：记录是否改变技术契约；改变则同步权威规范、代码与测试对应关系；未改变则说明 `DOC-NONE`；实际验证状态和待办可追溯。

**集成/版本 DoD**：按接收方范围检查所需手册、协议、构建/烧录/升级方式与发布资料；核对目标版本、软硬件/工具兼容、操作及失败路径、已知限制和实际验证证据；完成所需审查授权。没有正式外部交付需求时，不强制制造“客户版”文档。

## 11. 与现有 Skill 的关系

`embedded-design-decision` 负责设计决策文档，`embedded-code-reader` 负责源码阅读笔记，`extracting-chip-hardware-facts` 负责芯片/板级事实报告，`embedded-code-development` 负责已明确的代码实现与相关说明。它们**不等于**完整的文档发布/审核系统。V1.2 不新增或假定已存在独立 Documentation Skill；若以后发现稳定的重复失败场景，再按仓库规则独立评估。
