# 企业级嵌入式软件项目开发工作流（V1.1）

- 版本：V1.1
- 日期：2026-10-20
- 适用：需要持续维护、协作、迭代或正式交付的完整固件项目及大型固件子系统
- 目标：需求可追踪、设计可解释、变更可控制、行为可验证、版本可维护
- 定位：**嵌入式软件工程师的固件研发指南**，不覆盖硬件设计、结构、生产制造或其他岗位的独立职责


## V1.1 重要变化：全局契约与局部反馈的两层流程

外层建立软件需求、硬件/资源事实、稳定公共接口、ISR/Task/DMA 所有权与系统验收，不要求一开始写尽所有实现细节。将需求拆成**有独立验收的纵向切片（Tracer Bullet）**，每个切片独立执行 Design → Implement → Verify → Feedback；单一任务仍完成一次循环。

设计变化若影响公共 API、持久化/升级格式、安全策略或共享资源，必须回外层确认并评估先前切片。局部 PASS 仅证明本片验收，不等于整个固件的稳定性、系统集成、长稳或正式发布门禁已通过。依赖任务必须等前片验证；只有边界清楚的独立切片适合并行，公共接口及共享状态要有唯一写入者。

下文每个阶段分别标出现有 Skill 与**未开发的候选 Skill**，不将候选误认为已安装。


## 1. 范围、优先级和裁剪

本流程涵盖固件需求到软件发布及维护：设备驱动/BSP、RTOS、通信协议、存储、Bootloader/OTA、业务逻辑、日志诊断、软硬件联调、软件质量验证与版本管理。硬件原理图、接口电气、板卡修订版和芯片勘误是软件设计的输入；固件工程师需要核实并协作解决问题，但不承担硬件电路或产线工艺的整套工作流。

**采用顺序**：法律法规、适用行业标准和团队正式流程 > 已批准的项目要求与架构 > 已验证的软硬件事实 > 本文建议。存在冲突应提请项目责任方裁决，不由 AI 擅自取舍。功能安全、网络安全或监管要求按真实产品适用范围落实，不能把本文当作认证清单。

项目应按风险、规模和责任划分流程强度。单型号、低风险产品不自动引入多产品平台、微服务式层级或庞大文档体系；有多人协作、长期兼容、安全/实时要求时，才增强正式审查、基线、追溯和版本门禁。

## 2. 公共阶段总览

| 阶段 | 核心输入 | 主要输出 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| E0 项目接入与基线 | 需求、团队规范、现有仓库/设备 | 工程范围、环境与风险基线 | 权限、目标、构建/调试途径明确 |
| E1 软件需求定义 | 产品要求、接口约束、故障后果 | 软件需求与验收标准 | 关键歧义关闭，未决项有负责人 |
| E2 技术事实与约束核对 | 板卡、芯片、现有代码、厂商资料 | 事实清单、资源预算、未知项 | 影响设计的事实有依据 |
| E3 软件架构与关键决策 | E1/E2、团队约定 | 模块边界、接口、运行模型、风险与测试策略 | 核心决策得到所需评审 |
| E4 实施切片与计划 | 已接受的需求/设计 | 依赖明确的任务和验收用例 | 切片可单独验证，责任清晰 |
| E5 分切片设计/实现/验证 | 单项切片、基线、测试方案 | 每片设计/实现/测试/反馈证据 | 每片通过才能继续其依赖任务 |
| E6 集成和分层验证 | 集成固件、需求追踪、风险清单 | 功能/异常/资源/板级验证结果 | 发布所需关键证据完整 |
| E7 审查与版本交付 | 变更、测试、已知问题 | 审查结论、构建产物、发布记录 | 发布决策由授权责任人确认 |
| E8 维护与复盘 | 缺陷、反馈、运行数据 | 缺陷闭环、经验和后续改进 | 记录可追踪，变更重入合适阶段 |

上述阶段是逻辑活动而非一次性瀑布门槛。探索性实验、设计、编码和验证可迭代；关键基线变化需要同步更新相关要求与证据。

## 3. 逐阶段执行规范

### E0｜项目接入与工作基线

**本阶段 Skill**：现有可用：[embedded-code-reader](../skills/embedded-code-reader/SKILL.md)（现有源码）、[embedded-resource-acquisition](../skills/embedded-resource-acquisition/SKILL.md)（缺资料时）。**可能开发（未开发）**：暂无：优先既有构建工具。


- 阅读项目 AGENTS.md、README、架构/编码/分支规范、交付与保密要求；明确软件负责范围和其他团队接口。
- 确认版本管理、目标芯片/板卡、工具链、构建 Target、调试方式以及已知缺陷；已有工程先建立构建基线，不在未知状态上大幅修改。
- 识别数据安全、实时性、可靠性和时间约束中真正影响软件开发的因素。

**最小产物**：项目工作范围、复现构建的方法、关键风险、约束及未知项；不自动创建额外管理文档。
**退出条件**：工程可以以约定方式访问、构建或说明不能构建的阻碍；目标边界明确。

### E1｜软件需求质询与验收定义

**本阶段 Skill**：现有可用：[embedded-design-decision](../skills/embedded-design-decision/SKILL.md)（仅技术决策阶段；尚无专门需求 Skill）。**可能开发（未开发）**：embedded-requirements-clarification（定向需求质询）。


- 针对行为、边界、失败语义、性能、升级/兼容、诊断、安全相关约束进行定向追问。
- 将需求写成可观察或可测量的行为，给出正常、边界、异常用例；明确“不做什么”和需求来源。
- 分开记录已批准要求、假设和待裁决问题。AI 可以协助找漏洞，不代替产品/项目负责人批准需求。

**最小产物**：可追踪的需求项（编号或稳定链接）、验收条件、待决事项。
**退出条件**：影响接口、存储布局、执行模型或故障处理的关键要求已确认；否则标明阻塞，不以未经批准的假设推进不可逆方案。

### E2｜硬件事实、资源和既有软件约束

**本阶段 Skill**：现有可用：[embedded-resource-acquisition](../skills/embedded-resource-acquisition/SKILL.md)、[extracting-chip-hardware-facts](../skills/extracting-chip-hardware-facts/SKILL.md)；存量代码用 [embedded-code-reader](../skills/embedded-code-reader/SKILL.md)。**可能开发（未开发）**：暂无：优先现有能力。


- 根据精确器件型号、封装、板卡版本和修订版核实 Datasheet、Reference Manual、Errata、原理图及供应商软件包。
- 评估 Flash/RAM/栈、CPU 占用、时钟、DMA、IRQ、带宽、功耗、外设所有权、启动/升级分区、非易失存储寿命与异常恢复边界。
- 分开“手册保证”“现有源码表明”“推测需要实验”和“板级实测”。

**最小产物**：来源可追踪的硬件事实与资源预算、设计风险及验证办法。
**退出条件**：关键资源冲突和硬件能力不存在无根据假设；未知项拥有验证计划。

可按需使用 [embedded-resource-acquisition](../skills/embedded-resource-acquisition/SKILL.md)、[extracting-chip-hardware-facts](../skills/extracting-chip-hardware-facts/SKILL.md) 和既有工程的 [embedded-code-reader](../skills/embedded-code-reader/SKILL.md)。

### E3｜软件设计与设计审查

**本阶段 Skill**：现有可用：[embedded-design-decision](../skills/embedded-design-decision/SKILL.md)。**可能开发（未开发）**：暂无：不另造设计 Skill。


- 定义模块职责、依赖、接口契约、错误码、状态与数据模型；共享资源必须明确所有者。
- 明确 ISR、DMA、RTOS Task、IPC、超时与 deadline、缓冲区溢出、竞争条件、初始化/退出次序。
- 对高风险模块设计失败检测、隔离、恢复与安全状态；对升级和存储设计断电一致性、镜像校验、回滚以及版本兼容约束。
- 选满足要求的最低必要复杂度；只有实际变化轴、成本和收益支持时才引入平台化抽象。
- 在设计阶段决定测试接缝、可观测性、需要的 Host Fake/Mock、目标板验证以及测试专用入口与 Release 的隔离策略。
- 关键决策按需保留 ADR，术语确有歧义才维护 Glossary。

**最小产物**：有可检验接口及运行模型的软件设计、风险与测试策略、需要决策者批准的问题。
**退出条件**：关键设计决策经项目规定的评审，未决高风险项不得隐性落入代码。

可使用 [embedded-design-decision](../skills/embedded-design-decision/SKILL.md) 形成设计候选，但其输出不等于正式评审批准。

### E4｜任务拆分与追踪

**本阶段 Skill**：现有可用：[embedded-design-decision](../skills/embedded-design-decision/SKILL.md)（提供阶段路线）。**可能开发（未开发）**：embedded-task-decomposition（功能切片/依赖）。


- 把设计拆为能够独立观察行为的纵向切片（Tracer Bullet），必要时先建设环境、平台基础或测试接缝。
- 每项任务记录“实现什么行为 / 修改哪些边界 / 依赖谁 / 怎样验收 / 谁负责”；没有真实依赖不要制造串行阻塞。
- 小批量集成，尽早连通真实硬件路径，而不是各层长期孤立开发。
- 建立轻量追踪：需求 → 设计决策/模块 → 任务/变更 → 测试结果；可使用现有 Issue/PR 工具，不要求额外平台。

**最小产物**：可执行任务及依赖关系、每项验收条件、集成顺序。
**退出条件**：下一批任务边界清楚，可在明确环境中验证。

### E5｜每个切片的设计—实现—验证—反馈小循环

**适用范围**：企业固件的每个可验证子任务；如果无法合理拆分，则将整个任务视为一个切片。已有通过验证的切片是下一切片的基线。**小循环必须发生在每个切片内部，而不是做完全部设计和编码后只验证一次。**

#### E5-D｜Design：切片局部设计

- **输入**：该切片目标、外层确认的接口与硬件事实、已通过的前置切片。
- **动作**：确认需要修改的范围、接口/任务/ISR/DMA 与资源所有权、核心状态流、正常与关键失败路径；为本片制定测试输入、预期结果、环境与失败判据。
- **输出及出口条件**：简短切片设计卡（目标/非目标、边界、取舍、验收用例、前置依赖）；没有会改变实现的关键未知项。
- **已有 Skill**：[embedded-design-decision](../skills/embedded-design-decision/SKILL.md)（有实质设计取舍时）；[embedded-code-reader](../skills/embedded-code-reader/SKILL.md)（已有工程需核对调用关系时）。
- **未来候选 Skill（未开发）**：embedded-requirements-clarification（仅歧义阻碍设计时）；不再另造重复的设计 Skill。

#### E5-I｜Implement：最小编码与构建

- **动作**：只实现当前切片的可观察行为；同步必要工程文件/配置，遵守项目架构和生成代码边界。纯逻辑或可控测试接缝适合 Red → Green → Refactor；不要求所有硬件依赖路径都先写 Host TDD。
- **输出及出口条件**：本片 diff、实际 Target 的构建结果和可供测试的产物；**编译通过不是验证通过**。
- **已有 Skill**：[embedded-code-development](../skills/embedded-code-development/SKILL.md)。
- **未来候选 Skill（未开发）**：暂无新编码 Skill 需求；避免复制现有 Implement/Modify/Port。

#### E5-V｜Verify：实际执行验收

- **动作**：运行计划中的 Host 测试、目标板功能/边界/异常用例和必要时序/资源测量。对 DMA、ISR、RTOS、OTA/Flash 等行为，应依据风险取得 J-Link/RTT/逻辑分析仪/复位与故障注入等真实证据。
- **输出及出口条件**：记录环境、版本、输入、预期、实际、证据位置和 PASS/FAIL/BLOCKED。源码证据、编译、Host、板级、系统回归分别报告；没有执行不得写 PASS。
- **已有 Skill**：[embedded-code-development](../skills/embedded-code-development/SKILL.md) 负责已批准的局部测试入口、模块自测和实现相关检查；**尚无独立测试执行 Skill**，仍需真实工程工具和人员执行。
- **未来候选 Skill（未开发）**：embedded-test-verification（独立执行、记录并核对测试证据）。

#### E5-F｜Feedback：分析结果、修正、回归、关闭切片

- **PASS**：对照需求/工程规范做轻量自检并保存已验证 commit、测试证据与任务状态，然后开始下一项依赖切片。
- **FAIL**：保留最小复现和观测；实现缺陷回 E5-I；局部接口/算法错误回 E5-D；若波及公共 API、存储格式或全局资源所有权，则升级到外层设计/批准阶段，同时检查之前通过的切片是否受影响。
- **BLOCKED**：说明缺失设备、环境或依赖及恢复条件；不允许假设测试通过或推进依赖任务。
- **已有 Skill**：[embedded-code-reader](../skills/embedded-code-reader/SKILL.md)（读码定位）、[embedded-design-decision](../skills/embedded-design-decision/SKILL.md)（需要回设计时）、[embedded-code-development](../skills/embedded-code-development/SKILL.md)（明确缺陷后修复）。
- **未来候选 Skill（未开发）**：embedded-code-review（独立审查）、embedded-debugging（根因不明）、embedded-work-handoff（长任务交接）。

**退出条件**：本切片验收证据成立，且与已验证基线的必要兼容检查通过。**所有切片通过仍需外层跨切片集成回归与交付/复盘。**

### E6｜集成、验证与可靠性评估

**本阶段 Skill**：现有可用：[embedded-code-reader](../skills/embedded-code-reader/SKILL.md)（排查）、[embedded-code-development](../skills/embedded-code-development/SKILL.md)（修复）；真实执行仍依赖工程测试工具。**可能开发（未开发）**：embedded-test-verification、embedded-debugging。


按项目风险选择层级，而非机械要求每项都执行所有测试：

1. **静态与构建**：编译、链接、配置、内存布局、静态检查；验证目标 Target 和 Release 排除要求。
2. **Host 局部验证**：纯逻辑、协议解析、状态机、边界值及关键错误路径。
3. **目标板与软硬件联调**：外设、IRQ/DMA、调度、时序、功耗、启动流程、通信链路。
4. **系统与故障场景**：长稳、负载、资源耗尽、连接中断、复位、掉电/升级恢复、异常输入、故障注入（按适用风险）。
5. **回归**：核心已交付行为和受影响模块接口，避免新功能破坏旧行为。

测试结果应含环境（板卡/固件/Target/工具版本）、操作、预期、实际、结果、证据位置和未验证项。运行日志可作为证据之一，但不自动证明时序或边界正确。

**退出条件**：有风险依据的关键验收项通过；未完成项、已知缺陷及残余风险有明确处理决定。

### E7｜代码审查、发布与交接

**本阶段 Skill**：现有可用：[embedded-code-reader](../skills/embedded-code-reader/SKILL.md)（只读证据，不等于审查）。**可能开发（未开发）**：embedded-code-review（Spec/Standards/Evidence）。


- **规格审查**：是否实现确认过的行为和失败语义，需求变更是否已同步。
- **规范/架构审查**：是否遵守接口、编码、资源所有权、并发、内存、错误处理及安全边界。
- **验证证据审查**：编译、测试、硬件运行证据是否与声称的结论匹配。
- 根据项目要求检查依赖版本与许可、构建可复现性、版本号、升级兼容、回退路径、产物校验和发布说明。
- 使用授权的审查、签署和发布流程；AI 无权代替责任人审批、烧写生产设备或宣布对外发布。

**最小产物**：审查结论、修复关闭情况、固件产物与来源、测试状态、已知风险、恢复/回退说明。
**退出条件**：项目规定的责任人接受交付。不能把“AI 审查通过”当成正式批准。

### E8｜缺陷维护与工程复盘

**本阶段 Skill**：现有可用：[embedded-code-reader](../skills/embedded-code-reader/SKILL.md)；架构变化用 [embedded-design-decision](../skills/embedded-design-decision/SKILL.md)。**可能开发（未开发）**：embedded-debugging、embedded-work-handoff。


- 保存缺陷的真实症状、复现条件、影响版本、根因、修复及回归证据；未知根因不按猜测固化。
- 反思哪些要求、观测手段、构建检查或设计约束本可以更早发现问题，并以最小必要改动更新标准或工具。
- 新需求或架构变化按影响范围回到 E1/E2/E3；局部修复可直接采用 [既有工程模块工作流](existing-module-v1.1.md)。

## 4. 分级质量门禁

| 情形 | 必要重点 | 可按需加强 |
| --- | --- | --- |
| 简单低风险独立功能 | 正确性、构建、局部验证、变更说明 | 完整架构评审、多份专项计划 |
| 并发/协议/存储/升级等中高风险模块 | 状态与所有权、错误恢复、边界用例、板级/回归证据 | 故障注入、压力/长稳、跨版本兼容 |
| 长寿命/多型号/多人维护的固件系统 | 稳定接口、需求追踪、发布基线、协作审查 | 系统化自动化、性能预算跟踪、产品族演化治理 |
| 受安全或法规约束的软件 | 符合具体适用标准与正式组织流程 | 由适用条款进一步确定 |

## 5. 面向 AI 的协作与交接规则

- AI 可用于需求质询、方案比较、资料核实、任务拆分、代码实施、测试设计和双维审查，但必须给出证据与未知项。
- 在跨会话交接时只保留任务目标、已批准决定、代码基线、当前结果、未关闭风险、下一步及其验证方式；不要把聊天历史视为唯一事实源。
- 企业源码、内部资料、证书、密钥和客户数据遵守公司保密及 AI 使用政策；未经批准不得上传外部模型或仓库。
- 并行 Agent 仅处理真正独立的读任务或隔离实现；共享配置、公共 API、状态机和集成构建实行明确负责人。
- AI 提议的新抽象、测试框架或工具只有提供实际收益并经过设计判断后才引入。

## 6. 一次软件版本交付的 DoD

- [ ] 软件需求、风险和变更范围可追踪。
- [ ] 关键硬件事实、接口、资源与并发约束有依据。
- [ ] 设计/评审决定及未决事项可查询。
- [ ] 构建目标、版本、依赖和产物可复现或可核对。
- [ ] 需求相关测试、板级验证与回归结果可核实。
- [ ] 已知缺陷、残余风险、兼容性和回退方式已交接。
- [ ] 完成项目要求的授权审查与交付。

## V1.1 Skill 开发方向与约束

跨三套流程最值得先试验的候选是 **embedded-task-decomposition**（把设计拆成可验证切片）、**embedded-test-verification**（独立执行并核实 Host/板级/回归证据）、**embedded-code-review**（分开 Spec/Standards/Evidence 审查）。**embedded-debugging**（根因未知）、**embedded-requirements-clarification**（需求歧义）、**embedded-work-handoff**（跨会话长任务）按实际高频失败场景再决定是否开发。

**这些都尚未开发**；不要调用不存在的 Skill。一个候选 Skill 只解决一个独立、重复的工程问题；先建立失败基线，再按仓库 [AGENTS.md](../AGENTS.md) 验证显式触发、隐式触发、误触发与核心行为。完整路线图在 [工作流索引](README.md)，参考 [Matt Pocock 的方法](https://github.com/mattpocock/skills) 和 [本仓库设计框架](../skills/embedded-design-decision/references/decision-framework.md)。
