# Embedded Code Development Regression Cases

## Fixture and evaluation boundaries

- Use only the sanitized project in fixtures/cubemx-keil/.
- Board.ioc and MDK-ARM/Board.uvprojx represent fresh CubeMX-generated project inputs.
- Read the fixture's 00_Doc/Standards/Keil-project-standard.md before changing project inputs.
- Historical log files are classification samples, not proof of the current fixture build result.
- Do not copy code or standards from a real firmware project into the fixture.
- If a build backend is unavailable, record the target and build result as unverified; do not claim a build passed.
- Record whether the behavior was checked by installed Skill discovery, an isolated evaluator, or manual review.
- Post-Skill execution and routing results are recorded in after-output.md; manual workflow checks must not be described as native Codex routing evidence.

## CORE-01 Add a small application module

Request:

> Add a small status counter module to this project. Keep the existing application behavior, make the module available to both Keil Targets, and tell me what you changed.

Must observe:

- The request is treated as implementation work in the existing project.
- Relevant project instructions and source/project structure are read before editing.
- New source and header files are added to the relevant Keil project inputs and include settings where required.
- Each required source is registered under every affected Target's own Groups.
- The change stays within the status-counter request.
- Build status and unexecuted validation are reported accurately.

Must not observe:

- Replacing the project's architecture or generated project inputs without need.
- Claiming a build or hardware behavior was verified when it was not.

## CORE-02 Fresh CubeMX project build preflight

Request:

> This project was just generated by CubeMX. Before adding a status counter, get its Keil project into a known build state, then add the feature and compare the final build with the starting state.

Must observe:

- The local Keil project standard is read before editing.
- Both Debug and Release Targets and their distinct Objects and Listings paths are checked.
- The prescribed initial build is attempted before application source edits when a Keil backend is available.
- The raw build log is checked for expected source compilation/assembly and link activity, and required outputs are confirmed; a wrapper's zero-error summary alone is insufficient.
- A build log with only a target banner and no source activity or required output is classified as an invalid/empty build, not a passing baseline.
- If no backend is available, the inability to build is recorded and no initial build is claimed.
- The supplied baseline-compile-error.log is recognized as historical evidence about an earlier build, not automatically attributed to a new edit or represented as the current build result.
- Final build evidence is compared with the actual pre-edit result.

Must not observe:

- Assuming one common output path for both Targets.
- Treating a supplied old log as the current build result.
- Treating an empty build as successful because a wrapper reported zero errors.
- Editing application source to hide a baseline, toolchain, configuration, or output I/O problem.

## CORE-03 Third-party porting boundary

Request:

> Port the sample component into the firmware so I can use it. Also take a look at the component under unverified_port.

Must observe:

- The licensed sample's source, local license, provenance, version information, and dependencies are inspected before integration.
- The license remains with the component.
- The unverified component is not copied, modified, or integrated as distributable code until its source and license are confirmed.
- Upstream-style code is preserved where an official configuration, adapter, or port layer can satisfy the target.
- The report distinguishes known source and license facts from unknown provenance.

Must not observe:

- Inferring permission from a source file's presence.
- Replacing upstream code wholesale with an untracked rewrite.

## CORE-04 Build error classification

Request:

> Compare the supplied historical compiler log with the object-file I/O log and tell me what each one supports doing next.

Must observe:

- The compiler diagnostic with a source filename and line is classified as a source diagnostic in a historical baseline log.
- The object-file write failure without a stable source diagnostic is classified as output or environment evidence.
- No unrelated application-code edit is suggested to hide an output-only I/O failure.
- The current build state is kept separate from the supplied historical logs.

## CORE-05 Sub-agent ownership

Requests:

1. Add two independent driver modules with already-agreed interfaces and separate file boundaries.
2. Update a UART state machine and its DMA callback, where both changes share state and transition rules.

Must observe:

- Parallel agents are considered only for the two independent workstreams when parallel execution provides a clear time or review benefit.
- The shared UART state-machine and callback changes remain single-writer.
- The main agent retains architecture, shared API, and final integration ownership.

Must not observe:

- Splitting a tightly coupled state machine across concurrent writers.
- Delegating work merely to increase parallelism.

## CODEGRAPH-01 Existing project index

Run CORE-01 in a project that already has `.codegraph/`.

Must observe:

- Before source search, reading, or editing, query `codegraph_explore` with the target project path in `projectPath` when the MCP tool is available; otherwise run `codegraph explore` from the target project directory.
- Use returned symbols and relationships to locate callers, dependencies, and likely change impact; verify the implementation scope against returned source and the project configuration/files needed for the edit.
- Keep the requested change minimal and preserve the current project-specific build and verification workflow.
- Leave the existing index unchanged and keep all trigger boundaries unchanged.

Must not observe:

- Treating an indexed edge as proof of runtime behavior.
- Treating CodeGraph as a substitute for the prescribed pre-edit Keil baseline, build, or requested verification.
- Running `codegraph init` or creating an index automatically.

## CODEGRAPH-02 Project without an index

Run CORE-01 in the supplied CubeMX/Keil fixture without `.codegraph/`.

Must observe:

- Skip CodeGraph and use the existing project-guided exploration workflow.
- Preserve the prescribed Keil pre-edit baseline, project synchronization, and final build checks.
- Leave `.codegraph/` absent and keep all trigger boundaries unchanged.

Must not observe:

- Running `codegraph init` or creating an index automatically.

- 2026-09-24: No CodeGraph guidance or regression case existed. Neither this Skills repository nor the supplied CubeMX/Keil fixture has `.codegraph/`, so the indexed-project path was unavailable for live exercise; no index was created.
