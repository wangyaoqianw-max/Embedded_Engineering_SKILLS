# Embedded Design Decision Framework

## 证据顺序

按以下顺序处理冲突：

```text
当前项目的可验证事实
> 用户明确给出的需求与约束
> 已验证的稳定决策规则
> 候选工程经验
> 通用示例和惯例
```

无法验证的信息不得写成事实。需求与项目事实冲突时明确指出，并在继续前确认会改变架构的冲突。

## 范围分类

### Enterprise Product

完整产品具有长期维护、多型号、多人协作、量产可靠性或稳定演化要求。允许增加支持这些驱动因素的稳定边界，但不自动引入平台化、插件化或完整治理体系。

### Personal Project

个人完整项目保留必要模块边界、基本错误处理和合理演化空间。优先可理解、可验证和能在现有资源内完成，不照搬企业治理。

### Existing Project Module

已有工程中的局部模块默认服从现有架构、平台、接口风格、运行模型和规范。若这些事实未提供且会改变接入方式，先索取相关文件；不能用通用分层代替真实工程事实。任务只设计当前模块及接入边界，不借机重构整个产品。

## 架构驱动因素

只保留会改变设计的因素：

- 功能目标、任务边界和明确非目标。
- 现有工程架构、接口和约束。
- MCU、Flash、RAM、外设、功耗和时间预算。
- deadline、阻塞、ISR、DMA、并发和共享状态。
- 故障后果、恢复策略和长期运行要求。
- 已发生或有明确依据的移植、复用和演化需求。
- 产品规模、生命周期、型号数量和协作边界。

不能说明会改变哪项设计的因素，不得单独推动复杂度升级。

## 复杂度等级

复杂度按子系统判断，不给整个工程机械打一个总分。Application、Bootloader、诊断和单个模块可以使用不同等级。

### L0 直接实现

- 进入证据：单一职责、控制流简单、资源单一、没有独立并发或真实变化轴。
- 典型边界：少量函数或一个状态结构，直接由主循环或已有执行上下文调用。
- 过度设计信号：为一个 LED、按键或单次转换引入 Manager、Event Bus、插件、RTOS Task 或多层接口。
- 输出深度：只写必要接口、状态、资源、失败边界和最短实施顺序。

### L1 模块化

- 进入证据：职责需要独立测试或复用，存在清楚的硬件/业务边界，但没有复杂并发和平台级演化压力。
- 典型边界：一个内聚模块、窄接口、显式状态和薄平台适配。
- 过度设计信号：为假设中的未来变化建立通用服务注册、运行时多态或跨模块消息基础设施。

### L2 分层与服务化

- 进入证据：存在独立 deadline、多个执行上下文、共享外设所有权、平台迁移、多个业务调用者或必须隔离的故障域。
- 典型边界：Application/Service/Platform/Implementation 中实际需要的部分，或明确的 owner task 与消息通道。
- 过度设计信号：每个函数一层、每个外设一个 Task、重复抽象 RTOS 原语，或没有变化证据的通用框架。

### L3 产品平台化

- 进入证据：多个产品型号、长期兼容、多人并行开发、稳定产品族接口或受控演化是已确认需求。
- 典型边界：稳定领域接口、产品变体配置、版本兼容、系统级诊断和可验证的故障隔离。
- 过度设计信号：只有单一产品或单一实现，却提前建立插件市场、动态发现、全局服务容器或复杂元数据系统。

选择能够满足已知约束的最低等级。局部升级复杂度时说明具体驱动因素和影响范围。

## 模块和依赖

每个候选模块必须回答：

- 它唯一负责什么，不负责什么。
- 输入、输出和失败语义是什么。
- 依赖哪些稳定接口，谁依赖它。
- 谁持有可变状态，状态生命周期是什么。
- 失败会传播到哪里，如何隔离或降级。

依赖指向更稳定的策略或契约。不能回答这些问题的“层”通常只是增加跳转，应合并或删除。

## 运行模型和所有权

先判断以下事实，再选择主循环、状态机、DMA、ISR、Task、队列、事件或锁：

1. 哪些工作有独立 deadline 或必须隔离的阻塞。
2. 哪些动作必须在 ISR 中完成，哪些必须延后。
3. 数据由谁生产、谁消费，是否允许丢失或覆盖。
4. 外设、缓冲区和可变状态的唯一所有者是谁。
5. 队列容量、栈、静态内存和最坏处理时间如何验证。

资源所有权不清时，不进入接口细化。优先通过单一 owner 消除共享写入；只有确实需要并发访问时才引入互斥。

## 抽象证据

引入抽象至少需要说明：

- 真实变化：已经存在多个实现，或变化有明确项目依据。
- 传播成本：不隔离时，一次变化会修改哪些模块、测试或构建配置。
- 净收益：替换、测试、移植或局部修改收益大于 Flash、RAM、时序、理解和调试成本。

证据不足时保持简单。设计模式用于描述合适的职责与协作，不作为增加层级的理由。

## 过度设计与设计不足

### 过度设计信号

- 抽象只服务一个实现，且没有明确变化证据。
- 简单同步功能被拆成多个 Task、Manager、Bus 或注册中心。
- 接口数量和配置项显著多于当前行为。
- 设计文档在 L0/L1 场景深入到与决策无关的实现细节。
- 引入机制却无法指出它解决的当前约束。

### 设计不足信号

- 共享外设、缓冲区或状态没有所有者。
- ISR、DMA、Task 或主循环之间的数据流不清。
- deadline、容量、栈、Flash/RAM 或掉电一致性没有验证方法。
- 只有正常流程，没有错误、恢复、降级或安全状态。
- 平台变化直接传播到稳定业务或服务逻辑。

每项新增机制都要指出它解决的当前约束；每项关键约束都要能在设计中找到对应决策。

## 实施路线

按依赖关系裁剪以下阶段，不机械套用固定清单：

1. 关闭会改变架构的未知项，固化需求和资源基线。
2. 建立最小可观测性和失败证据。
3. 验证平台、外设、存储或时序边界。
4. 实现被上层依赖的稳定接口和核心服务。
5. 实现业务行为和异常路径。
6. 完成资源、实时性、故障注入和系统级验证。

每个阶段说明输入、可验收输出和进入下一阶段的条件。路线到可执行顺序为止，不继续代替编码或测试 Skill 执行工作。

## 文档自检

写入前检查：

- 输出目录和文件名明确，同名文件不会被覆盖。
- 事实、假设和未知项分开；没有未解释的占位符。
- 任务范围和各子系统复杂度有依据。
- 模块、依赖、运行模型和资源所有权一致。
- 关键失败路径、拒绝方案和验证项完整。
- 文档深度与 L0～L3 相称，没有为满足模板而扩写。
- 实施路线按依赖排序，且文档在设计阶段停止。
