# Keil 工程接入与构建基线

按需读取：任务涉及刚由 CubeMX 生成的 Keil 工程、Keil 工程配置、构建输出目录，或编译/链接结果与修改前状态比较时。

## CubeMX 新生成项目的初始化边界

本流程从 CubeMX 已经生成 .ioc 和 Keil 工程文件（通常为 .uvprojx）开始。Skill 不负责生成新的 Keil 工程，不自行选择芯片、Target、启动文件、内存映射、Scatter File 或工具链版本。所需输入缺失或存在歧义时先询问。

在修改应用源码前：

1. 阅读目标项目的 AGENTS.md、Keil 构建规范和 CubeMX/Keil 工程输入。
2. 从工程文件枚举实际 Target；逐个检查对象文件和 Listing 的输出设置。
3. 将每个 Target 的输出设置与项目本地规范比较。发现不一致时，由代码开发流程修正工程配置并记录初始化改动；不得套用其他项目的目录值或通用默认值。
4. 仅在本地规范要求目录预先存在时创建输出目录。构建期间生成的目录由构建工具按配置创建。清理前核对精确路径和内容，只处理可再生输出。
5. 若目标或配置不清楚、项目输入损坏，或修复会改变芯片内存布局、Target 含义等设计决策，暂停并询问；不要把初始化扩展成重建工程。
6. 配置符合项目规范后，使用匹配的 Keil 构建能力，对项目要求的每个 Target 执行规定的首次 Build 或 Clean Rebuild，再开始应用代码修改。
7. 核对原始构建日志确实包含预期源码的编译/汇编记录和链接结果，并确认项目要求的输出产物存在。只有“Rebuild target”或包装器报告 0 errors/0 warnings、但没有参与源码和产物的空构建，不算有效基线；先检查 Target 的 Groups 和工程输入是否正确。
8. 记录工程/Target、操作类型、工具链信息、错误和警告、日志位置、有效产物，以及 git status 中的相关变化。将初始化配置变更与应用功能变更分开说明。

首次构建失败时，先保留结果并分类，不把尚未编写的代码列为根因。历史日志只能作为历史证据，不能替代本次实际构建。

## 源码与工程文件同步

- 新增、移动或改名的源文件必须加入所有需要它的 Keil Target；检查 Include Path、预处理宏和 Target 间差异。
- 修改工程文件前先看该文件现有的 Target/Group 结构，按项目实际格式做局部修改。不要用通用 XML 模板覆盖 CubeMX/Keil 生成内容。
- 构建工具负责扫描和构建，不负责替代码开发流程修正工程配置。若 Keil/GCC/EIDE Skill 明确不修改工程输入，由本 Skill 按任务范围完成配置接入后再调用构建。
- CMake、Make、EIDE 等工程也按相同原则同步清单、配置和目标选择，但遵从各自项目规范。

## 修改前后构建比较

完成首次基线后再改应用代码；代码和工程接入完成后，按项目流程重建受影响 Target。工程配置的初始化构成基线的一部分，应记录初始化前后的配置差异。

比较时区分：

- 代码诊断：有稳定源码文件、行号或符号位置的编译/链接错误。
- 工程配置问题：文件未加入 Target、Include Path、宏、链接输入或目标设置不一致。
- 工具链/环境问题：编译器、Pack、许可证或工具不可用。
- 输出 I/O 问题：对象文件写入失败、Invalid argument 等，且没有稳定源码诊断。

只有基线没有的新增错误才可能由当前修改引入；逐条检查证据。随机对象文件 I/O 失败优先核对 Target 输出路径、占用、权限和环境，不改无关业务代码掩盖它。

Build、Clean 和 Rebuild 通过项目已有 Keil Skill 或项目指定入口执行。清理、关闭工具、改变系统设置前按项目规则核对目标和授权；本参考不授权删除输出、修改安全软件配置或清理用户目录。
