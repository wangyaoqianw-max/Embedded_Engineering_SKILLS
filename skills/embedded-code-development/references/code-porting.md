# 代码移植与第三方接入

按需读取：将第三方库、开源组件、Vendor 代码、其他 MCU 平台代码或可复用模块接入目标工程时。

## 移植前核对

先查目标工程是否已有同类实现，再确认：

- 来源仓库或供应方、版本/tag/commit；无法确认时标为未知，不编造。
- LICENSE、版权声明、NOTICE 和再分发/修改条件。文件存在不等于许可明确。
- 源码、头文件、配置、汇编/启动代码、链接输入及其依赖。
- MCU 架构与 ABI、编译器、RTOS/裸机、平台接口、内存与并发约束，以及异常和日志出口。
- 目标工程当前实现、生成代码边界和可接受的适配范围。

来源、许可或用户对修改归属的要求不明确且会影响集成时，先询问。不要把来源不明的代码复制、改写或纳入可分发产物。

## 适配顺序

优先级从窄到宽：

1. 使用上游正式配置、目标平台已支持的实现或编译选项。
2. 在目标项目的 adapter、port 或 platform 层适配。
3. 做局部、可追踪的上游补丁，并记录补丁差异及升级影响。
4. 只有没有更窄方案且用户需求明确时，才修改第三方核心代码。

保持上游文件和版权/许可材料可识别。不要把整体重写后仍称为原组件，也不要为格式统一重排整份上游源码。

移植验证应覆盖该组件使用的目标架构和构建 Target，并按项目要求检查接口、配置和必要测试。无法实机验证时说明限制，不将编译通过写成运行行为正确。

## 资产归属与结果记录

- 未经适配的第三方原始代码放在 Library 的 third_party。
- 已形成跨项目通用适配的代码放在 Library 的 adapted。
- 只服务当前固件的端口层和项目胶水留在当前工程。
- 复制、移动、发布或更新 Library 资产必须属于当前任务范围；没有授权时只在目标工程内完成必要集成。

交付时记录已确认的来源与版本、许可文件位置、目标依赖、适配文件、上游改动、工程接入方式和验证范围。含义不明确的简称（例如 cmk）先确认组件名，不推定为 cmBacktrace。
