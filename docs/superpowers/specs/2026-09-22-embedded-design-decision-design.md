# Embedded Design Decision Skill 设计规格

## 目标

创建仓库的首个正式 Skill：`embedded-design-decision`。

该 Skill 面向嵌入式产品或模块在编码前的工程设计决策。它根据需求、现有工程事实、硬件资源、实时性、可靠性、复用性和演化约束，选择足够且不过度的设计复杂度，并把结论写成指定目录下的 Markdown 设计文档。

Skill 在输出设计文档后结束，不继续编写业务代码、构建、烧录、调试或执行测试。

## 成功标准

- 能区分企业完整产品、个人完整项目和已有工程模块三种任务范围。
- 能选择满足已知约束的最低设计复杂度。
- 能给出模块边界、依赖方向、运行模型、资源所有权、关键接口和实施路线。
- 能识别过度设计与设计不足。
- 能按问题需要选择性读取参考资料，而不是把所有资料装入上下文。
- 用户未指定输出目录时先询问；指定后生成一份可独立阅读的 Markdown 设计文档。
- 不越权进入编码、构建、烧录、调试或测试执行阶段。

## 范围

### 应触发的请求

- 新嵌入式产品编码前的架构与开发路线设计。
- 判断个人项目应采用多复杂的工程结构。
- 设计已有工程中新模块的边界、接口和接入方式。
- 选择 RTOS 任务、事件、资源所有权与并发模型。
- 设计 Bootloader、OTA、存储或平台迁移方案。
- 判断是否需要抽象层、适配器、状态机或其他设计模式。
- 审查现有设计是否过度设计或设计不足。

### 不应触发的请求

- 直接编写或修改业务代码。
- 编译、烧录、在线调试和通信抓包。
- 单纯解释某个 API、协议或设计模式。
- 定位和修复已有缺陷。
- 执行测试、发布、项目排期、BOM 或供应链管理。

## 文件职责

### `SKILL.md`

保持精简，只包含：

- 触发范围与排除范围。
- 输出目录前置条件。
- 范围分类和核心决策流程。
- 参考资料的按需路由规则。
- 设计文档的内容合同。
- 停止边界与安全约束。

### `references/decision-framework.md`

作为每次调用都需要读取的稳定决策内核，包含：

- 三种任务范围的处理差异。
- 架构驱动因素。
- 复杂度等级及选择规则。
- 模块、依赖和接口边界。
- 运行模型与资源所有权。
- 必要抽象的证据要求。
- 过度设计与设计不足检查。
- 实施路线的排序原则。

### `references/engineering-experience.md`

作为新工程经验的候选池。每条经验记录来源场景、问题、决策、结果、适用条件、不适用条件和状态。候选经验不得直接作为强制规则。

### 三份现有参考资料

- GoF 蒸馏：为变化隔离、抽象、接口和设计模式判断提供依据。
- FreeRTOS 报告：为任务、ISR、IPC、实时性、内存和并发决策提供依据。
- Bootloader/OTA 报告：为启动、升级、分区、回滚和镜像安全决策提供依据。

### 测试材料

- `baseline.md` 记录没有目标 Skill 时，各场景的实际输出和具体失败。
- `regression-cases.md` 记录场景输入、预期决策、不应出现的行为和验证结果。

测试关注可观察决策，不匹配固定标题、措辞或文档段落。

## 输入处理

### 输出目录是强制前置条件

用户必须指定设计文档的输出目录。未指定时，Skill 先询问目录，不自行选择默认位置，也不开始生成最终设计文档。

文件名遵循以下优先级：

1. 用户指定的文件名。
2. 目标目录已有的设计文档命名规范。
3. `YYYY-MM-DD-主题-设计.md`。

目标文件已存在时不得直接覆盖。应先请求确认，或在不改变用户意图的前提下使用新的明确文件名。

### 事实优先

开始决策前，读取用户提供的需求、当前工程、已有架构文档和项目规范，并把信息分成：

- 已验证事实。
- 明确假设。
- 未知项。

会改变架构选择的关键约束缺失时先询问。非关键事实缺失时可以继续，但必须在文档中标注假设和验证项。无法验证的硬件参数、实时指标和安全结论标记为“未验证”。

当前项目的可验证事实优先于通用参考资料。需求与工程事实冲突时明确指出，不静默选择一方。

## 范围分类

### Enterprise Product

面向长期维护、多型号、多人协作或产品级可靠性的完整产品。除通用约束外，可以考虑团队协作、生命周期和产品变体，但 V0.1 不扩展到组织管理、法规认证、供应链、BOM 或项目排期。

### Personal Project

面向个人学习、验证或可维护的完整项目。保留必要的模块边界、错误处理和演化空间，不机械采用企业级治理与抽象。

### Existing Project Module

面向已有工程中的局部模块。默认服从现有架构、平台、运行模型、接口风格和规范，只设计当前模块及其接入边界，不借任务重构整个系统。

## 决策流程

```text
确认输出目录
    ↓
读取需求、现有工程和已有设计文档
    ↓
区分事实、假设和未知项
    ↓
判断任务范围
    ↓
识别真正的架构驱动因素
    ↓
选择最低可满足需求的复杂度
    ↓
设计模块、依赖、运行模型和资源所有权
    ↓
检查过度设计与设计不足
    ↓
生成实施路线
    ↓
写入设计文档
```

关键架构驱动因素限于会改变设计的内容：

- 功能目标和任务边界。
- 现有工程架构与规范。
- MCU、存储、外设和资源预算。
- 实时性、并发和阻塞条件。
- 可靠性与故障处理要求。
- 移植、复用和预期变化。
- 产品规模与生命周期。

## 复杂度等级

- `L0 直接实现`：简单裸机功能、单一职责、变化很少。
- `L1 模块化`：存在明确模块和接口，但不需要通用服务体系。
- `L2 分层与服务化`：存在并发、资源所有权、平台隔离或多个业务模块。
- `L3 产品平台化`：多型号、长期演化、多人协作或稳定平台边界成为主要驱动。

复杂度等级是决策工具，不是全工程的机械评分：

- Application 与 Bootloader 可以使用不同等级。
- 只有受约束影响的子系统才提升复杂度。
- Existing Project Module 默认继承现有工程等级。
- 始终选择能够满足已知约束的最低等级。

## 抽象和设计模式

抽象需要证据，至少说明：

- 存在真实变化或明确的高概率变化。
- 变化会产生值得控制的传播成本。
- 新增间接层的收益大于资源、理解和调试成本。

证据不足时保持简单。设计模式只用于解释合适的职责与协作结构，不作为套用模式或增加层级的目标。

## 参考资料路由

- 每次调用读取 `decision-framework.md`。
- 涉及抽象、变化隔离、接口或设计模式时读取 GoF 蒸馏。
- 涉及任务、ISR、IPC、实时性、内存或并发时读取 FreeRTOS 报告。
- 涉及启动、升级、分区、回滚或镜像安全时读取 Bootloader/OTA 报告。
- 存在相似工程场景时读取 `engineering-experience.md`，但候选经验只作为参考。
- 不因资料存在而无条件加载全部文件。

## 设计文档合同

最终交付是一份写入用户指定目录的 Markdown 设计文档。文档应独立可读，并按任务规模调整深度，至少覆盖：

1. 背景与目标。
2. 任务范围。
3. 已知事实、假设和未知项。
4. 关键约束。
5. 架构驱动因素。
6. 复杂度选择及依据。
7. 模块边界与依赖方向。
8. 运行模型与资源所有权。
9. 关键接口。
10. 资源规划。
11. 可靠性与故障策略。
12. 不采用的设计及理由。
13. 风险与验证项。
14. 按依赖关系排列的分阶段实施路线。

聊天回复只概述文件位置、核心结论和未确认项。

## 错误与停止条件

- 未指定输出目录时暂停并询问。
- 关键事实缺失且不同答案会改变架构时暂停并询问。
- 目标文件可能被覆盖时暂停并确认。
- 无法验证的信息进入假设或验证项，不编造结论。
- 设计过程中不修改业务代码、构建配置或工程结构。
- 设计文档写入并核验后停止，不进入实现阶段。

## V0.1 验证设计

### 六个核心场景

1. GPIO、LED、按键：保持 `L0`，不引入 Device Manager 或 Event Bus。
2. UART DMA、RingBuffer、FreeRTOS：识别 ISR 到 Task 的数据流和 UART 所有权。
3. STM32F4 Bootloader：保持精简，不机械套用 RTOS 和完整应用分层。
4. Bootloader、OTA、A/B、Rollback：分别判断 Application 与 Bootloader 的复杂度。
5. F411 到 F407、W25Q64 到 W25Q128：识别平台迁移变化轴，保护稳定服务边界。
6. 已有公司工程中的 Sensor Module：只设计模块及接入边界，不重构整个产品。

### 触发和行为验证

- 显式调用能够触发。
- 架构设计类请求能够隐式触发。
- 编码、构建、烧录、调试和纯概念解释不会误触发。
- 未指定输出目录时先询问。
- 指定目录后生成设计文档。
- 不无条件加载全部大型参考文件。
- 输出能区分事实、假设和未知项。
- 输出同时说明推荐设计和明确不推荐的设计。

## 经验迭代机制

经验按以下路径成熟：

```text
engineering-experience.md
    ↓ 形成可复现场景
regression-cases.md
    ↓ 多次验证且边界明确
decision-framework.md
    ↓ 只有流程或路由改变
SKILL.md
```

单个项目经验不能直接形成全局规则。规则升级前应明确适用条件、不适用条件和至少一个能观察其作用的回归场景。废弃经验保留状态与原因，避免以后重复引入。

V0.1 使用可审查的场景、输入、预期决策和实际结果进行验证。只有重复执行成本明显增加时，才引入自动化测试脚本。

## 非目标

- 生成或修改嵌入式业务代码。
- 替代构建、烧录、调试、通信或测试 Skill。
- 建立完整的项目管理和产品治理体系。
- 把三个参考报告改写成百科全书式 `SKILL.md`。
- 因单个项目经验增加全局强制规则。
- 在 V0.1 中建立插件、MCP 服务或复杂自动化工具。
