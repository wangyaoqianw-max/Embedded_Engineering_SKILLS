# 嵌入式代码开发 Skill 设计规格

## 目标

创建一个面向已有嵌入式工程的代码实施 Skill，将已明确的功能要求、修复要求或施工方案落实为代码修改、工程接入和可说明的构建结果。

Skill 覆盖三种工作模式：

- Implement：实现新模块或功能。
- Modify：修改已有模块、驱动、Service、Platform 或 Application。
- Port：移植和集成第三方、开源或跨平台代码。

三种模式共享工程理解、变更范围控制、工程配置同步和结果整合流程。移植细节按需读取参考资料。

## 成功标准

- 修改前确认目标、现有架构、工程规则、构建入口和变更范围。
- 项目事实及项目级规范优先于通用建议。
- 采用满足需求的最小必要改动，避免无关重构。
- 对 CubeMX 新生成的 Keil 工程，在代码修改前完成项目规定的首次构建预检，并记录基线。
- 新增或移动源文件时同步相关工程文件和构建配置。
- 将实际构建交给已有的 GCC、Keil 或 EIDE 构建能力；Skill 负责选择时机、检查结果和修复本次改动导致的编译或链接问题。
- 移植工作记录来源、版本、许可、依赖、适配边界和验证范围。
- 仅在独立工作流并行能明显节省时间或提高审查质量时使用子代理。
- 最终报告实际改动、构建状态、已执行测试以及未执行的验证。

## 适用范围

### 应触发

- 实现已经明确的嵌入式施工方案。
- 为现有工程新增或修改驱动、模块、服务或应用功能。
- 将已有的库、组件或平台代码移植到目标工程。
- 修复已有代码中的明确缺陷。
- 同步新增源文件、头文件、配置或构建工程文件。
- 修复与本次代码或工程接入相关的编译、链接问题。

### 不应接管

- 需求或系统架构尚未确定的设计任务；转入 embedded-design-decision。
- 只要求理解现有源码且不要求修改的任务；转入 embedded-code-reader。
- 根因未知的运行时故障；转入 Debug 工作流。
- 独立的功能测试、硬件验证或代码质量审查。
- 构建工具、烧录工具或调试工具本身的实现和维护。
- 未经明确要求的项目发布、提交、推送或外部写入。

输入不足以确定功能行为、资源所有权、关键接口或目标平台时，先询问或回到设计阶段，不以实现选择代替缺失的架构决策。

## 信息优先级

按以下顺序处理规范和事实：

1. 用户当前明确要求。
2. 目标工程的 AGENTS.md、README、设计文档、构建规范和真实工程配置。
3. 已确认的设计或施工方案。
4. 用户指定或当前环境可访问的通用代码规范。
5. 本 Skill 的通用开发建议。

项目规范与通用规范冲突时，确认项目约束并记录必要例外。不要把单个项目的目录结构、芯片选择、工具链版本或输出路径变成全局默认值。

## 工作流程

### 1. 判断任务是否已具备实施条件

确认目标功能、目标工程、目标平台和已有设计的明确程度。需求或架构决策会显著影响实现时，先澄清，不直接改代码。

### 2. 读取必要的工程上下文

先阅读适用的工程规则和现有构建说明，再定位相关源码、接口、调用方、配置和工程文件。仅扩展到支撑当前修改所需的范围。

确定当前采用的工程、Target 或构建配置。存在多个候选且无法从项目状态确认时，询问用户。

### 3. 建立修改前构建基线

对已有工程，检查当前可用的构建状态。对用户说明为新建、刚由 CubeMX 生成或尚无首次构建结果的 Keil 工程，将首次构建作为代码修改前的预检：

- 定位 CubeMX 工程文件和 Keil 工程文件，枚举实际 Target。
- 阅读目标项目提供的 Keil 构建规范；检查每个 Target 的输出配置是否符合该规范。
- 规范要求初始化配置或执行 Clean Rebuild 时，按其步骤验证；不以 Skill 的通用默认覆盖项目规范。
- 检查生成输出应落入项目规定位置，并确认源码、工程输入与可再生构建输出边界清楚。
- 记录工具链、Target、构建类型、错误和警告，以及 Git 状态中的相关变化。

构建失败时，先分类为源码诊断、工程配置问题、工具链/环境问题或输出 I/O 问题。基线失败不自动归因于尚未实施的代码改动。

清理或删除构建输出前，核对精确目录并确认其中只有可再生生成物；不删除或改写项目输入。

### 4. 确定最小变更并实施

在满足需求的前提下控制修改范围。尊重既有目录、接口、命名、错误处理和资源所有权。避免无关重构以及未经确认的公共 API、数据结构、全局配置或跨层架构调整。

项目采用的 C 代码规范可用时，按适用范围和项目裁剪要求执行。第三方、Vendor SDK 和自动生成代码保留其来源约定；确需修改时识别文件归属并限制差异。

### 5. 执行移植或第三方集成

移植前确认代码来源、版本、许可证、依赖、目标架构、编译器、RTOS、平台接口、异常/日志出口及目标工程已有实现。

默认优先保持上游实现，通过官方配置方式、平台端口层或 adapter 完成适配。仅在有具体证据且无更窄方案时修改上游核心代码，并记录差异和升级影响。

按复用范围选择资产归属：第三方原始代码归入 Library 的 third_party；经过实质适配且可跨项目复用的代码归入 adapted；只服务当前固件的适配留在目标工程。实际复制、移动或发布资产须属于用户当前任务范围。

### 6. 同步工程文件并构建

代码改动需要更新源文件清单、Keil 工程、CMake、EIDE 或其他构建输入时，由代码开发流程负责所需的工程接入修改，并遵守项目规范。实际构建调用匹配的构建 Skill，不重复实现构建工具。

工程文件修改后以及代码集成完成后，按项目流程构建。将结果与修改前基线比较，只针对本次变更引入的编译或链接问题迭代修复。不要为绕过环境或 I/O 失败而修改无关业务代码。

Keil 报告随机变化的目标文件写入失败、Invalid argument 等错误且缺少稳定的源码诊断时，优先检查 Target 输出配置、文件占用、路径和构建环境；只有编译器给出可定位到源码的诊断时，才按代码错误处理。清理输出、关闭工具或调整系统设置须遵守项目规则和操作授权。

### 7. 测试与交付

按用户要求和目标工程既定流程执行验证。没有执行的测试或硬件验证如实标记；成功构建不等于功能或硬件行为已验证。

最终说明：

- 改动范围及工程文件同步情况。
- 采用的构建工程、Target、构建类型和结果。
- 实际执行的测试与结果。
- 未执行或无法确认的验证。
- 移植来源、许可证、修改范围和已知限制（适用于移植任务）。

## 子代理使用

只有同时满足“存在两个及以上独立工作流”和“并行可明显节省时间或提高分析、实现或审查质量”时才使用子代理，不为提高并行数而拆分紧密任务。

同一个文件、紧耦合模块、共享状态机或正在共同设计的接口保持单一写入者。子代理可承担只读分析、独立模块工作、构建日志分析或独立审查。

架构边界、公共 API、跨层调用、共享数据结构及全局工程设置由主代理统一决策。主代理在交付前检查架构、API、子任务冲突、工程配置、整合后的构建结果、已执行测试以及未执行的验证。构建期间不得并行修改参与构建的输入或清理其输出目录。

无论是否使用子代理，主代理对最终结果负责。子代理结果是中间材料，不能替代整合后的工程验证。

## 规范与参考资料的存放

- 不把 Library 中的《嵌入式项目 C 代码设计规范 V2》复制到 Skill references；在可访问时按目标工程裁剪要求查用该唯一版本。
- Keil 工程输出和构建规范留在目标项目，由 Skill 在 CubeMX/Keil 工程初始化或修改时读取并遵循。
- Skill 的 references 仅保存代码开发流程自身需要的条件性内容，例如第三方移植步骤或构建错误分类；不得复制单个项目的绝对路径、工具链路径或专用目录布局。
- 不因一个 CubeMX/Keil 项目的经验制定所有工程必须使用相同 Objects、Listings 或输出目录的全局规则。

## V0.1 回归场景

1. **明确施工方案的新模块**：先检查当前工程结构和接口，实施必要代码与工程接入，构建并报告结果。
2. **已有模块内的耦合修改**：由一个写入者完成状态机和回调修改；不按文件片段强拆子代理。
3. **CubeMX 新建 Keil 工程**：先读取本地 Keil 规范，完成首次基线构建和 Target 输出检查，再编辑代码；报告基线与最终构建差异。
4. **第三方组件移植**：核对来源、版本、许可证与依赖；优先使用上游配置或 adapter；不因示例而假定 cmk 的具体含义。
5. **Keil 输出 I/O 错误**：随机对象写入失败且无源码诊断时进入环境/输出路径排查，不直接改业务 C 代码。
6. **两个独立驱动并行开发**：仅在接口已确定、文件边界互不冲突时并行；主代理完成 API 与完整工程检查。
7. **误触发边界**：源码只读解释、架构设计、独立构建、未知运行时故障、独立测试或 Code Review 不由本 Skill 接管。

实现前在无目标 Skill 的条件下运行代表性场景并记录失败基线。Skill 实现后验证显式调用、隐式触发、非触发边界、工程集成、构建基线处理、移植行为和多代理整合规则。测试关注可观察结果，不匹配固定措辞。

## 非目标

- 把代码开发 Skill 做成新的构建、烧录、调试、测试或代码审查工具。
- 默认生成 CubeMX 工程、推测 MCU/Target/工具链配置，或修改 CubeMX 输入文件。
- 无需求地清理、移动或提交构建产物。
- 要求每项代码修改都运行完整功能测试或实机验证。
- 把 Library 或单个 Firmware 项目的完整标准复制到 Skill。
- 未经任务授权创建、发布、推送或提交第三方资产。
